# tyohnn portfolio

연주환의 채용용 기술 포트폴리오 기획서다. 무엇을 만들었는지 나열하기보다,
여러 해 동안 같은 기술적 질문을 어떻게 더 깊게 고민해 왔는지 보여준다.
프로젝트는 그 질문과 판단을 검증하는 근거다.

현재는 Next.js 앱을 `apps/web`에서 개발한다. 페이지 기획의 SSOT는 이 README다.

```bash
pnpm dev
```

## 포트폴리오가 보여줄 한 가지

> 복잡한 현실의 모델을 설계하고 추상화합니다. 다양한 관점에서 최적해를 찾는 것을 선호합니다.

> **3년간 집중하고 있는 것** 사람과 에이전트가 같은 맥락 위에서 협업할 수 있는 환경을 만들고자 합니다.

이 문장은 “어떤 제품을 만드는 사람”보다 “어떤 기술적 질문을 오래 붙잡아 온
사람”인지를 설명한다.

- **무엇을 데이터로 남길 것인가**: 현실의 대상을 어떤 단위와 생명주기의
  레코드로 추상화할지.
- **관계와 다형성을 어디까지 열 것인가**: 서로 다른 데이터의 공통점과 차이를
  어떻게 모델링하고, 자유도와 정합성 사이의 경계를 어디에 둘지.
- **누가 그 기록을 신뢰하게 할 것인가**: 사람, 에이전트, 배치가 같은 SSOT를
  다룰 때 권한, 검증, 이력, 검토를 어떻게 보장할지.

`SSOT`, `SoR`, `다형성`은 프로젝트 설명에서 근거와 함께 사용한다. 히어로에서는
처음 보는 사람도 이해할 수 있도록 “함께 신뢰하는 기록”, “어떻게 관계 지을지”,
“서로 다른 형태를 어디까지 함께 다룰지”로 번역한다.

## 독자가 얻어야 하는 인상

페이지를 3분 본 독자는 다음을 알아야 한다.

1. 프론트엔드와 백엔드를 모두 만들 수 있지만, 중심 역량은 **데이터 모델과
   서버 정합성 설계**다.
2. 그래프나 다형성을 무조건 선호하지 않는다. 도메인에 필요할 때 열고,
   관계가 정해진 업무에서는 타입과 제약을 닫는다.
3. 에이전트를 채팅 UI가 아니라 **도구 계약, 기록, 권한, 검토 흐름을 가진
   작업자**로 다룬다.
4. 프로젝트 이름보다 질문의 변화가 먼저 보이고, 각 프로젝트는 그 판단을
   내리게 된 증거로 기능한다.

## 엔지니어링 원칙

Hero 바로 아래, Skills보다 앞에 다섯 개의 카드로 둔다. 방법론을 나열하는 대신
어떤 실패를 막기 위해 선택하는지 설명하고, 각 카드에서 실제 프로젝트와 기술
글로 연결한다. 문장 SSOT는 [`docs/content/principles.md`](./docs/content/principles.md)다.

- **비트겐슈타인 논리철학논고형 엔지니어** — 노션 블록, 프레이머/피그마를
  리버스 엔지니어링으로 참고하며 데이터를 범용적으로 추상화하고 관계·다형성을 남긴다.
- **도메인 중심으로 사고하는 엔지니어** — 도메인 로직과 데이터 모델을 먼저
  설계하고, 헥사고날 구조와 Port/Adapter로 외부 의존성을 분리한다.
- **에이전트의 컨텍스트를 모국어처럼 이해하는 엔지니어** — 툴 콜링, RAG,
  스킬, Compaction으로 여러 턴이 지나도 동작이 이탈하지 않게 설계한다.
- **에이전트와 협업을 설계하는 엔지니어** — 코드 규약과 신뢰할 수 있는
  작업 환경을 설계하고, 구조·도메인·시스템을 먼저 고민한다.
- **서버 보안에 집착하는 엔지니어** — 각 경계는 이전 단계의 출력을 믿지
  않고, deny-all RLS를 최후의 보루로 둔다.

## 3. 계속 붙잡아 온 세 가지 질문

이 섹션이 사이트의 본문이다. 각 질문은 짧은 소개, 현재의 답, 답이 바뀐 과정,
근거가 된 프로젝트, 아직 남은 질문으로 구성한다.

### 무엇을 하나의 데이터로 남길 것인가

현실의 업무를 어떤 레코드로 남길지 먼저 정한다. 캔버스의 블록, 네이버 검색
순위, 회사 도메인의 노드와 엣지, 기간별 재무 계정은 모양은 다르지만 모두
“무엇을 하나의 사실로 저장할 것인가”라는 질문에서 시작했다.

현재의 답은 데이터 모델이 UI의 저장 형식이 아니라, 사람과 소프트웨어가 같은
대상을 다시 판단할 수 있게 하는 계약이어야 한다는 것이다. 원본 사실, 현재
상태, 파생 결과의 생명주기를 구분하고 정정 이력을 덮어쓰지 않는다.

### 관계와 다형성을 어디까지 열 것인가

여러 형태의 데이터를 하나의 인터페이스로 다루고 관계로 연결하는 데 관심이
있다. 동시에 모든 도메인에 범용 그래프가 필요한 것은 아니라는 것도 배웠다.
열린 캔버스에서는 다형성이 제품의 핵심이었지만, 법무·회계처럼 관계가 정해진
업무에서는 타입과 연결 규칙을 서버에서 닫는 편이 낫다.

현재의 답은 다형성과 관계를 기능으로 먼저 열지 않고, 실제 도메인에서 변하는
축을 확인한 뒤 여는 것이다. 자유로운 표현이 핵심인 UX에서는 열되, 정합성이
핵심인 기록에서는 허용 타입과 관계를 닫는다.

### 사람과 에이전트가 같은 기록을 어떻게 신뢰할 것인가

에이전트가 안정적으로 일하려면 프롬프트보다 먼저 읽을 데이터, 호출할 도구,
변경할 수 있는 범위가 있어야 한다. 결정적인 기본 로직은 제품이 제공하고,
에이전트는 예외와 여러 단계를 잇는 작업을 맡는다. 모든 변경은 사람이 검토할
수 있는 기록으로 남긴다.

현재의 답은 에이전트를 기록 시스템 밖의 자동화로 두지 않는 것이다. 사람과
같은 SoR을 읽되, 도구 스키마와 서버 권한으로 쓸 수 있는 범위를 제한하고,
게이트와 이력으로 결과를 다시 검토할 수 있게 한다.

## 4. 이 질문을 발전시키는 기술 에세이

추천 목록에 있던 글은 부가 콘텐츠가 아니라 포트폴리오의 중심 서사다. 홈에서는
각 글의 핵심 판단과 변화 과정을 보여주고, 카드에서 독립 아티클로 연결한다.

### 데이터 모델의 세대 — 자유도와 정합성 사이

상태 기반 모델에서 지식그래프, 다형 캔버스, 타입 카탈로그 그래프로 이동한
과정을 쓴다. “그래프가 더 좋은 모델인가”가 아니라, 어떤
도메인에서 관계와 다형성을 열어야 하고 언제 닫아야 하는지가 중심이다.

근거: 2023 Fynd → 2025–2026 ssota note → 2026 ssota.

### 에이전틱 워크플로우 — 호출에서 책임 있는 작업자로

도구를 호출하는 에이전트에서 시작해, SoR을 읽고 쓰는 오퍼레이터와 그 변경을
승인하는 사람의 관계로 확장한 과정을 쓴다. Agent Tool 계약, 동적 작업 페이지,
게이트, 감사 가능한 기록이 이어진다.

근거: 2023 Veclix → ssota note의 캔버스 협업 → 2026 ssota →
oh-my-docs / never-sleep-agent는 회고 확인 후 추가.

### B2B SaaS의 기록 — 로직, SoR, UX를 어떻게 나눌 것인가

B2B SaaS를 도메인 로직, 기록 시스템, 사용자 경험의 세 층으로 본다.
결정론적인 기본 로직은 제품에 남기고, 사람 판단이 필요한 예외와 여러 단계의
연결만 에이전트에 맡겨야 한다는 현재의 판단을 설명한다.

근거: 크날의 반복적인 B2B 구현 경험은 역할 회고 후 보강하고, 현재는 ssota의
설계와 구현만 확정 근거로 쓴다.

## 5. 스택

단순 로고 벽이 아니라 채용 직군의 질문에 답하는 형태로 나눈다. 탭을 바꾸면
해당 분야의 기술과 이를 사용한 프로젝트 근거가 함께 보인다.

### Backend

- 최상: TypeScript, Node.js, Next.js, Zod
- 상: Python, FastAPI
- 하: NestJS, Django

### Frameworks & Frontend

- 최상: React, Next.js
- 중: Tailwind, Vue
- 하: Nuxt, React Native

### Database

- 최상: PostgreSQL
- 상: Supabase, Drizzle
- 중: Neo4j
- 하: MySQL, Redis

### Infra / Data

- 상: Vercel, Message Queue
- 중: Docker, Playwright, SEO
- 하: Railway, AWS S3, EC2, EB

### Agent

- 상: MCP, AI SDK
- 중: Langchain, RAG, Neo4j

기술 숙련도를 퍼센트나 별점으로 표시하지 않는다. `최상`은 본문에서 설계
판단과 한계를 말할 수 있는 기술, `상`은 프로덕션에서 반복해 쓴 기술,
`중`은 프로젝트 근거가 있는 사용, `하`는 썼지만 본문 근거가 짧은 기술이다.

## 6. 프로젝트와 연도는 근거다

프로젝트 목록은 핵심 질문과 에세이 뒤에 둔다. 각 프로젝트는 독립적인
성과 카드가 아니라, 특정 판단이 생기거나 바뀐 계기를 증명한다. 연도는
기술적 질문이 시간에 따라 어떻게 발전했는지 확인하는 보조 탐색축이다.

### 2026 — 열린 다형성에서 신뢰할 수 있는 기록으로

캔버스에서 여러 형태의 데이터를 자유롭게 잇던 모델을, 회사 업무의 타입과
관계를 서버에서 검증하는 기록 시스템으로 발전시켰다.

프로젝트:

- **ssota note**: 2D 공간의 다형 블록, 공통 셸, 동적 탭과 composition.
  관계를 시각화하는 대신 컴포넌트 데이터 흐름이 복잡해진 한계까지 설명한다.
- **ssota**: 회사 데이터의 타입 그래프, 서버 정합성, 동적 페이지, B2B SaaS의
  결정론 로직과 에이전트가 맡을 예외의 경계, deny-all RLS와 서버 권한,
  하네스와 샌드박스.
- **holiday-investment**: OpenDART 공시와 재무 데이터를 회사·기간·계정
  단위로 정리해 반복 조회할 수 있는 Postgres 정형 기록으로 DB화.

### 2024 — 대량 수집을 반복 가능한 기록으로

크날의 캐치블로그에서 네이버 검색 결과를 대량으로 수집하고 매일 갱신했다.
크롤러 자체보다 큐, 동시성, 서버리스 실행 시간, 중복을 막는 데이터 제약이
더 중요한 문제라는 것을 배웠다.

프로젝트:

- **캐치블로그**: cron이 작업을 큐에 넣고 Functions와 API가 분산 처리한다.
  `(keyword, date)` 유일성으로 동시 적재 중복을 닫았다. 큐는 Redis가 아니라
  Postgres 기반 PGMQ였다는 사실을 명확히 적는다.

### 2023 — 에이전트가 데이터와 도구를 쓰는 방법을 학습

초반에는 버디파이에서 Vue.js 프론트엔드를 만들었다. 이후 에이전트가 비정형
콘텐츠에서 장소를 추출해 관계로 연결하고, 외부 API를 하나의 도구 계약으로
호출하게 만드는 실험을 했다.

프로젝트:

- **버디파이**: Vue.js 프론트엔드. 제품 범위와 기여는 추가 회고 후 보강한다.
- **Fynd**: 여행 콘텐츠를 장소 데이터로 추출하고 Neo4j 지식그래프로 연결.
  완성된 SoR이 아니라 관계 모델을 학습한 단계로 표현한다.
- **Veclix**: 도구의 이름, 설명, 입력 스키마, 소유자, API 키 요구 여부를
  통일된 계약으로 등록·조회·실행. 훗날 MCP와 이어지는 관심의 시작으로
  설명하되 당시 구현을 MCP라고 부르지는 않는다.

카드 원문은 [`docs/content/cards.md`](./docs/content/cards.md), 자세한 근거는
[`docs/years`](./docs/years)에 둔다. 페이지에서는 프로젝트를 먼저 나열하지 않고,
각 기술적 질문의 근거 링크와 하단 타임라인에서 노출한다.

## 프로젝트 카드 구성

모든 프로젝트 근거 카드는 같은 구조를 사용한다.

1. **프로젝트와 기간** — 스택과 근거 링크
2. **개요** — 어떤 프로젝트였고 직접 붙잡은 범위가 무엇인지
3. **기술적 도전 목차** — 대표작 2–4개, 학습기 1개
4. **도전별 문제** — 기존 방식에서 무엇이 복잡했는가
5. **도전별 해결** — 어떤 경계와 구현을 선택했는가
6. **도전별 배움** — 이후 판단이 어떻게 달라졌는가
7. **도전별 한계** — 검증하지 못했거나 잘못 가정한 범위

접기/열기 단계는 두지 않는다. 개요와 도전 목차를 먼저 훑고, 목차 링크로
각 도전의 문제·해결·배움·한계에 바로 이동한다. 프로젝트 끝에서 배움과
한계를 다시 한데 요약하지 않고, 각각의 기술적 도전과 붙여 맥락을 보존한다.

## 시각 방향

- 인상은 “제품 랜딩 페이지”보다 **잘 편집된 기술 문서**에 가깝게 한다.
- 본문 폭은 긴 글을 읽기 편한 680–760px, 근거 타임라인은 필요할 때 더 넓게 쓴다.
- 배경과 타이포그래피를 중심으로 하고, 장식용 그라디언트와 과한 애니메이션은
  쓰지 않는다.
- 질문을 가장 크게, 현재의 답과 변화 과정을 그다음으로, 프로젝트 근거는
  작게 표시한다. `판단`과 `한계`는 색보다 구조로 구분한다.
- 기술 로고 대신 텍스트 칩을 쓴다. 브랜드 색이 정보 위계를 깨지 않게 한다.
- 모션은 헤더 이동과 언어 전환 정도로 제한하고
  `prefers-reduced-motion`을 따른다.

## 반응형과 접근성

- 모바일에서는 에세이와 프로젝트 근거를 한 열로 표시한다.
- 스택 탭은 가로 스크롤이 아니라 줄바꿈 또는 select 대체 UI를 사용한다.
- 모든 탭과 펼침 영역은 키보드로 조작할 수 있어야 한다.
- 의미 있는 heading 순서를 유지하고, 색만으로 숙련도나 상태를 구분하지 않는다.
- 한국어와 영어의 문장 길이가 달라도 레이아웃이 무너지지 않아야 한다.

## 콘텐츠 원칙

- 사용자 회고가 의도와 배움의 SSOT다. 코드, GitHub, Notion은 사실 확인에 쓴다.
- 확인하지 않은 사용자 수, 매출, 프로젝트 수는 공개하지 않는다.
- 숫자는 자랑이 아니라 설계 제약을 설명할 때만 쓴다.
- 팀 프로젝트는 직접 한 범위만 쓴다.
- 보안은 외부 입력 검증, 서버 권한, 마지막 잠금으로서의 deny-all을
  확인된 범위에서만 설명한다.
- 실패를 전시하지 않는다. 모델의 한계와 다음 판단으로 이어진 학습을 적는다.

## 완료 기준

- 히어로가 만든 결과보다 계속 붙잡아 온 기술적 질문을 설명한다.
