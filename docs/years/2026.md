## 1. ssota note / ssota-archive (사용자: 2025.08–2026.03)

로컬 `ssota-canvas` ≈ private `ssota-labs/ssota-archive`.
git: 첫 커밋 2025-07-21, 레포 생성 2025-09-24, HEAD 2026-03-05 (audio block, mobile drive).

### 한 일 (회고 전문)

텍스트, 이미지, 미디어, PDF, SNS, 웹 등 다양한 자료를 한 보드에 모으고
원본에서 텍스트 데이터를 추출했다. 자료 사이의 관계를 설정해 하나의 리서치
맥락을 만들고, 에이전트와 함께 리서치하는 보드를 만들고자 했다.

서로 다른 자료를 하나의 리서치 모델로 다루고 그 사이의 관계를 만들었다.
에이전트가 캔버스를 읽을 수 있도록 보드의 자료와 관계를 컨텍스트로 제공했다.

구현에서는 데이터 모델이 동적이었고, **2D 공간 위에서 노드와 엣지를 연결**해야
했다. 캔버스 위에서 동적으로 렌더되어야 했고, **같은 셸(당시 회고: HOC)로
감싸 같은 동작**을 제공하는 것이 중요했다. **탭**으로 화면을 동적으로 구성할
수도 있었다. UX 계층이 두꺼워질수록 composition을 쓰며 리팩토링했다.

코드: `block_type` enum 23종, `block_mounts`로 정체성/배치 분리, compound `BaseBlock`+`DataBlock`, 탭 레지스트리. Clerk는 11월에 빼고 Supabase Auth.

코드에서 확인된 모델 (설계 문서 `unified-database-schema.md`는 구형):

- `blocks`: `block_type` enum + `properties`/`content`/`metadata` jsonb
- `block_mounts`: 페이지 위 좌표·z·view_mode (`note`/`original`/`card`). 블록 정체성과 배치를 분리
- `edges`: mount-to-mount
- 공통 셸은 고전 HOC가 아니라 **compound `BaseBlock` + `DataBlock`(뷰모드)**. 타입 컨테이너가 도메인 훅을 꽂음
- 탭: `BlockEditorTabsConfig` 레지스트리, youtube/link/pdf/audio/x만 구현. `editor-panel` 패키지로 분리 중
- 인증: Clerk는 2025-11-23 제거, Supabase Auth

### 배운 것 (회고 + 코드)

- 다형성이 제품 핵심일 때는 스키마·렌더러를 타입별로 닫으면 안 된다. 최근 ssota보다 여기서 다형성이 더 중요했다.
- UX가 두꺼워질수록 composition이 필수. "노드로서의 동작"과 "타입별 내용"을 나눠야 한다.
- 공간은 관계를 보여주지만, 모델과 렌더 트리를 동시에 키운다.

### 고민 / 한계 (회고 + 코드가 같은 말을 함)

- 컴포넌트 사이 데이터 흐름이 복잡해져 이해가 어려워졌다.
- 모듈성 자체 평가 **stage 2/7**: 폴더만 DDD, 도메인 간 서비스 직접 import, ACL 거의 없음.
- 타입마다 tabs/schema/action/ai-definition 설정이 복제됨. `ssota-blocks`로 뺀 것은 youtube/x/link/audio뿐.
- **문제 정의가 열려 있었다.** 노트 + 코드 + 3D + "block = app" 피벗 문서가 공존.
- 2026.01에 canvasdown / spatial-context를 떼어 낸 것은, 캔버스 위에서 에이전트가 도구를 수십 번 치는 대신 DSL 한 방으로 그래프를 쓰게 하려는 잔상.

### 스택

Next 15, React 19, TS, `@xyflow/react` v12, TipTap 3, Supabase+Drizzle, TanStack Query, pnpm/turbo, Playwright. 설계 문서의 Clerk/`components` 테이블/`block_page_positions`는 현재 스키마와 불일치.

## 2. ssota / new-ssota (사용자: 2026.05–06)

공개 `ssota-labs/ssota` (레포 2026-06-10). 로컬 마이그레이션은 `20250611`(초기 스키마·RLS)부터. 5월 전용 `202605*` 파일은 없음 — 회고의 5월은 설계/노션, 6월이 스키마 커밋으로 보는 편이 맞다.

제품 문장: "Infrastructure for SaaS 2.0: Specialist + System of record."

### 한 일 (회고 전문)

팔란티어의 온톨로지 시스템을 **관계형 데이터베이스로 구축하려 한 시도**였다.
실제 업무 데이터는 노드라는 단 하나의 데이터 모델에 저장하고, 노드의 종류를
정의하는 노드 카탈로그와 관계를 정의하는 엣지 카탈로그를 두었다. 이 구조로
서로 다른 도메인의 데이터 모델을 정의하는 메타 모델을 만들었다. 정합성은
서버에서 처리하려 했다.

기업의 업무는 문서와 데이터로 분리되어 있다. 둘을 하나의 평면에 올려 관계를
만들고자 했다. 문서도 그래프 노드로 두고 기능 역할에 따라 분류했다. 문서
온톨로지에서는 State, Decision, Rule, Plan, Evidence, Narrative, Index,
Transaction을 구분하고 시간성·변경 가능성·권위 수준·생명주기 상태와 관계를
함께 정의했다.

- 근거:
  [온톨로지, 지식그래프, 컨텍스트 그래프 개념 정리 문서](https://paxhumana.notion.site/373346dac456807782d3d08ab91f1d13?source=copy_link)

Action과 Function을 정의해 그래프 데이터를 프로그래밍 방식으로 계산하고
조작하게 했다. JSON Render로 데이터 모델에 맞는 동적 대시보드 UI를 구성하고
액션과 연결했다. 그래프 데이터를 기반으로 워크플로우를 구성할 수 있도록
에이전트 환경도 구축했다.

동시에 B2B SaaS를 세 층으로 봤다.

1. 도메인/비즈니스 로직 (서버)
2. 이를 영속하는 DB — System of Record
3. 정형 도메인 로직과 유저가 만나는 UX

도메인 로직은 **Deterministic** 한 것과, 엣지케이스가 많아 사람 판단이 들어가는 **Non-deterministic** 한 것으로 나뉜다. AI가 없을 때 B2B 유저는 엣지케이스를 자기 지능으로 메웠다. 엣지케이스가 잦으면 그때마다 함수를 늘려 복잡도가 쌓였다. 그래서 에이전트가 SoR을 보고 도메인 로직을 **그때그때 쓰거나 저장**하는 방향을 생각했다. 한계는 모든 로직을 새로 쓸 필요는 없다는 것. **기본 deterministic은 제품이 주고, 엣지케이스와 체인만 에이전트**가 맡는다. 앞으로 사람보다 에이전트가 더 많이 작업하기도 해서 UX를 고정할 필요가 없어진다. 노션처럼 동적 페이지를 짰고, 에이전트가 페이지를 조립하는 데이터 모델도 짰다. 이때부터 **하네스 + 샌드박스**로 개발이 매우 빨라졌다.

한계로 말한 것: 특정 도메인 안 데이터끼리만 연결이 생긴다. 엣지/관계의 다형성이 제한되는 경우가 많다. 법무·회계는 정해진 관계만 있다. 다형성이 폭발하는 경우는 많지 않고, **크로스 도메인 연결 필요는 더 적다**.

### 코드가 회고를 수정하는 지점

노션 IA v2.7(2026-06-15)과 **현재 코드가 다르다.** 사이트에는 코드를 따른다.

| 노션 v2.7 / 1차 문서 | 현재 코드 |
| --- | --- |
| 카탈로그 = 플랫폼 전역 | 카탈로그 = **org-scoped** (`organization_id`) |
| 인스턴스 = `project_id` | `projects` → **teamspaces** (`teamspace_id`, 2026-06-28) |
| `allowed_pairs` v1 없음 | 엣지 **domain/range 배열**을 `GraphWritePort.createEdge`에서 강제 |
| 페이지 = 그래프 `page` 노드 | 전용 **`pages` 테이블** (`spec` json-render, `bindings`, `actions`) |
| 법무·회계 템플릿 암시 | 시드된 builtin은 **SWDL 하나** (`software-development`) |

정합성 층:

1. use-case: catalogKey 해석, 노드 속성 Zod (`validateNodeProperties`). 엣지 속성은 아직 pass-through
2. port: org 일치, domain/range, end-user는 `account_id` 자기 행만 쓰기
3. gate: `gate_policy` **노드**를 읽어 create/update/spawn 시 평가. 통과 시 spawn
4. RLS: 그래프·pages 등 deny-all. 서버는 admin DB bypass (`[SEC-01]`)

동적 페이지: `JsonRenderSpec` + 컴포넌트 카탈로그. MCP `create_page`/`update_page`. SWDL 시드에 페이지 트리 44장. 에이전트 authoring 스킬 `ssota-ax-author`.

하네스 (회고의 "이때부터 빨라졌다"의 실체 후보):

- `pnpm harness` = docs ↔ invariants ↔ ESLint ↔ 미러 동기화
- `check-boundaries` (직접 Drizzle CRUD 등 우회 탐지), `check-dev-identity` (워크트리 포트)
- Playwright 55스펙 (mcp-graph-write, end-user-app, work-cycle, sandbox, approvals)
- DB 샌드박스 환경 테이블 (2026-06-30)

보안 판단 (사용자 회고, 채용 포폴의 보안 축):

- **Defense in depth.** 외부 요청은 신뢰하지 않는다. Zod 등으로 입력을 먼저 닫는다.
- 복잡한 RLS 정책보다 **RLS `false`(deny-all)를 마지막 잠금**으로 둔다. 실제 권한은 서버·미들웨어 책임.
- 코드와 일치: `[SEC-01]` deny-all + admin DB bypass, `GraphWritePort`에서 org/domain/range/`account_id`, MCP는 툴마다 org 멤버십 재검증.
- 없는 것: 범용 graph mutation `action_log`(제거됨). 있는 것은 `agent_runs` 트랜스크립트와 매니저 승인 UI.

상세는 [themes/security.md](../themes/security.md).

### 배운 것

- 관계 다형성의 가치는 도메인에 따라 다르다. 닫힌 도메인에 범용 그래프를 열면 모델링 비용만 는다. (회고) 코드는 그래서 domain/range를 포트에서 닫았다.
- B2B 복잡도는 UI가 아니라 deterministic 로직 위의 사람 판단. 에이전트는 그 층만 대체.
- 에이전트가 1등 오퍼레이터면 페이지는 작업 화면이 아니라 승인·감사 화면. 그래서 `pages.spec`을 데이터로 둠.
- 정합성은 클라이언트 composition이 아니라 서버 포트. 캔버스 시절 복잡도 폭발이 배경.
- 속도의 레버는 하네스. 문서·불변식·검증을 에이전트가 우회 못하게 배선.

### 고민 / 한계

- 범용 KG를 회사 전체에 깔려 했으나, 실제로 시드해 돌린 템플릿은 SWDL. 법무·회계는 회고의 사고실험이거나 AX 샌드박스 수준 — **어느 쪽인지 확인 필요**.
- 카탈로그를 org로 내린 것은 v2.7 "전역 카탈로그"에서 후퇴/정교화. 고객사 온톨로지를 열 여지를 남김.
- 포지셔닝이 한 달에 여러 겹: 컨텍스트 그래프, Agentic Product OS, 코딩 에이전트 위 의사결정 SSOT.

### 스택

TS 모노레포 (pnpm/turbo), Next 콘솔, `@ssota/ui`, Supabase/Postgres, Drizzle, MCP, Playwright, 워크트리 하네스.

## 올해의 기술 arc

```
다형 캔버스 (23 enum × 뷰모드 × 탭, 클라이언트 composition)
    ↓ 복잡도 + 문제 정의 부재
    ↓ 부산물: canvasdown / spatial-context
타입 그래프 SoR (org 카탈로그, domain/range, pages 테이블, 게이트)
    ↓ 범용 그래프의 한계, 실제 시드는 SWDL
하네스 / oh-my-docs / never-sleep / holiday-cfo
    (에이전트가 제품을 만들거나, 원장을 건드리지 못하게 하는 쪽)
```
