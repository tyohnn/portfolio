# 히어로

특정 제품에 묶지 않는다. 2023–2026에 반복된 관심인 데이터 추상화,
관계·다형성, 사람과 에이전트가 공유하는 SSOT를 쉬운 말로 옮긴다.

**역할 (KO)**

> 복잡계를 모델링하는 소프트웨어 엔지니어

이름 아래 한 줄. 직군은 소프트웨어 엔지니어이고, 붙잡아 온 질문은
복잡한 업무·관계를 데이터로 남기는 일이다. 영어 `Engineer`만 두지 않는다.

**한 줄 (KO)**

> 복잡한 현실의 모델을 설계하고 추상화합니다. 다양한 관점에서 최적해를 찾는 것을 선호합니다.

**집중 (KO)**

> **3년간 집중하고 있는 것** 사람과 에이전트가 같은 맥락 위에서 협업할 수 있는 환경을 만들고자 합니다.

**보조 문장 (KO)**

> 데이터 추상화와 다형성에서 시작해 B2B SaaS의 System of Record, 에이전트의 도구 계약과 SSOT까지 같은 질문을 확장해 왔습니다.

**왜 이 문장인가**

- **복잡한 업무와 정보**: 여행 정보, 다형 콘텐츠, 회사 도메인, 검색 순위,
  재무 공시처럼 서로 다른 대상을 다뤘다.
- **어떤 데이터로 남기고 어떻게 관계 지을지**: Fynd 그래프, 캔버스 블록과 엣지, ssota의
  타입 그래프, 검색 순위와 기간별 재무 레코드 모두 “무엇을 사실로 남기고
  어떻게 연결할지”를 고른 작업이다.
- **사람과 에이전트가 함께 신뢰하려면**: Veclix의 도구 계약에서 ssota의 MCP,
  동적 페이지와 게이트까지 에이전트를 별도 데모가 아니라 같은 업무 기록을
  다루는 작업자로 설계했다.
- **무엇이 필요한지**: Zod, 서버 포트, 유일성 제약, append-only
  이력, RLS deny-all처럼 기록의 정합성과 권한을 서버에서 지켰다.

**히어로에서 번역한 말**

- 데이터 추상화 → “어떤 데이터로 남길지”
- 관계성·다형성 → “어떻게 관계 지을지”
- Agent SSOT / B2B SoR → “사람과 에이전트가 그 기록을 함께 신뢰하려면”

전문 용어는 버린 것이 아니라 기술 에세이와 프로젝트 근거에서 다시 설명한다.
히어로의 서술어를 “만듭니다”가 아니라 “고민해 왔습니다”로 둔 이유도 같다.
정체성을 특정 산출물이 아니라 반복된 기술적 질문에 둔다.

**쓰지 않는 문장**

- “그래프 SoR 엔지니어” — 2026만 설명함
- “풀스택 / AI 네이티브” — 비어 있음
- “데이터 추상화와 다형성을 설계합니다” — 정확하지만 처음 보는 채용 독자에게
  결과가 와닿지 않음
- 회사 미션, 팔로워, 수상
