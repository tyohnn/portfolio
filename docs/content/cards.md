# 페이지에 올릴 프로젝트 카드

히어로: [hero.md](./hero.md)

각 카드는 접지 않는다. `개요 → 기술적 도전 목차 → 도전별 문제 / 해결 / 배움 /
한계` 순서로 읽는다. 대표작은 도전 2–4개, 학습기와 짧은 합류 프로젝트는

이 구조 그대로 옮긴다.

## 2026

### holiday-investment

**개요.** OpenDART의 상장사 공시와 재무 데이터를 Postgres의 정형 기록으로
DB화한 개인 리서치 플랫폼. 외부 데이터를 반복해서 조회하고 활용할 수 있게
만드는 것이 목적이었다.

기술적 도전 섹션은 두지 않는다. 이 프로젝트는 별도의 난제를 해결한 사례보다
재무 데이터를 정형 기록으로 DB화한 경험으로 소개한다.

### ssota

**개요.** 팔란티어의 온톨로지 시스템을 관계형 데이터베이스 위에 구현해 보려
한 시도. 노드라는 하나의 데이터 모델과 노드 카탈로그, 엣지 카탈로그로 여러
도메인의 모델을 정의하는 메타 모델을 만들었다. 문서와 업무 데이터를 같은
그래프 위에 올리고, Action과 Function, JSON Render UI, 에이전트 워크플로우를
그 위에 연결했다.

문서 분류 근거:
[문서 온톨로지 설계](https://paxhumana.notion.site/373346dac456807782d3d08ab91f1d13?source=copy_link)

1. **하나의 관계형 메타 모델로 여러 도메인을 정의하기**
   - 해결: 실제 데이터는 노드로 저장하고, 노드 카탈로그와 엣지 카탈로그에서
     타입·속성·관계를 정의했다.
   - 한계: 실제로 시드해 반복해서 돌린 도메인은 SWDL 하나다.
2. **문서와 업무 데이터를 같은 평면에 놓기**
   - 해결: 문서를 State, Decision, Rule, Plan, Evidence 등의 기능 역할로
     분류하고 시간성·변경 가능성·권위·생명주기·관계를 함께 정의했다.
   - 배움: 문서도 데이터처럼 타입, 상태, 권위, 시간, 관계를 가져야 사람과
     에이전트가 같은 기준으로 읽을 수 있었다.
   - 한계: 실제 기업의 문서 수명주기와 권한 흐름에서 충분히 운영하지 못했다.
3. **비즈니스 로직을 매번 코드로 추가하지 않기**
   - 해결: 그래프의 상태를 바꾸는 Action과 데이터를 계산하는 Function을
     입력·실행 조건·결과가 있는 계약으로 정의했다.
   - 배움: 데이터의 종류와 관계뿐 아니라 무엇을 계산하고 바꿀 수 있는지도
     함께 정의해야 했다.
   - 한계: 여러 도메인에서 재사용성, 버전, 권한까지 충분히 검증하지 못했다.
4. **데이터 모델에 맞는 대시보드 구성하기**
   - 해결: JSON Render의 페이지 스펙과 데이터 바인딩을 데이터로 두어
     데이터 모델에 맞는 대시보드를 구성했다.
   - 배움: 페이지 구조와 데이터 바인딩도 함께 정의해야 새로운 도메인을 UI
     코드 수정 없이 표현할 수 있었다.
   - 한계: 동적 페이지도 SWDL 중심으로 검증했다.
5. **그래프를 읽고 실행하는 에이전트 워크플로우 만들기**
   - 해결: 에이전트가 MCP로 그래프를 읽고 Action과 Function을 호출하되,
     실제 쓰기는 같은 서버 포트와 검증을 통과하게 했다.
   - 배움: 에이전트에는 검색할 컨텍스트뿐 아니라 실행할 동사와 게이트가 필요했다.
   - 한계: 여러 기업 업무에서 장시간 운영하지 못했고 범용 변경 감사 로그도
     완성하지 못했다.

### ssota note

**개요.** 텍스트, 이미지, 미디어, PDF, SNS, 웹 등 다양한 자료를 한 보드에
모으고 원본 텍스트 데이터를 추출했다. 자료를 하나의 리서치 모델로 다루고
관계를 설정해 단일 리서치 맥락을 만들었다. 보드의 자료와 관계를 컨텍스트로
제공해 에이전트와 함께 리서치하고자 했다.

1. **서로 다른 콘텐츠를 같은 공간의 블록으로 다루기**
   - 해결: 정체성과 배치를 나누고 공통 셸 안에 타입별 내용을 조합했다.
   - 배움: 다형성이 제품이면 스키마와 렌더러를 타입별로 닫으면 안 된다.
   - 한계: 탭·스키마·액션 설정이 타입마다 반복됐다.
2. **공간이 만든 복잡한 데이터 흐름을 제어하기**
   - 해결: 셸과 타입 컨테이너의 책임을 나누고 일부를 DSL 방향으로 분리했다.
   - 배움: composition은 제품의 문제 정의까지 대신하지 않는다.
   - 한계: 노트·코드·3D·block-as-app이 동시에 열려 있었다.

## 2025

### 노벨라 스튜디오

**개요.** 소설 저작 어시스턴트. Langchain을 썼고, 작가의 문체, 기존 배경,
이전화, 등장인물 컨텍스트를 넣는 일을 고민했다. 단순히 써 주는 것을 넘어
종합적인 피드백 모드 같은 특화 모드도 만들고자 했다.

1. **이어지는 소설에 필요한 컨텍스트를 넣기**
   - 해결: 문체, 배경, 이전화, 등장인물을 컨텍스트로 넣으려 했다.
2. **쓰기만이 아닌 특화 모드 만들기**
   - 해결: 종합적인 피드백 모드 같은 특화 모드를 만들고자 했다.

## 2024

### 캐치블로그

**개요.** 네이버 검색 결과를 매일 수집해 블로그 키워드 순위를 쌓는 SaaS.
전문직 블로그 마케팅 대행사인 최블마케팅의 내부 툴로 사용했다. 파서보다
큰 배치를 반복하고 같은 사실을 중복 없이 남기는 일이 더 어려웠다.

1. **긴 일 배치를 서버리스 실행 시간 안에서 끝내기**
   - 해결: cron → PGMQ → Edge Function/Next API로 잡을 팬아웃했다.
   - 배움: 서버리스 배치는 재시도 가능한 작업 단위를 설계하는 문제다.
   - 한계: 일부 긴 경로는 늘린 타임아웃에 의존했다.

## 2023

### Veclix

**개요.** 에이전트가 서로 다른 외부 API를 발견하고 호출하게 만든 업무자동화
프로젝트. MCP의 개념을 직접 만들고 있었다.

1. **서로 다른 외부 API를 하나의 도구 계약으로 만들기**
   - 해결: 이름·설명·JSON 입력 스키마·소유자·API 키 여부를 한 계약으로 통일.
   - 배움: 에이전트는 채팅보다 먼저 읽을 수 있는 도구 계약이 필요하다.

### Fynd

**개요.** 여행 영상에서 장소 정보를 추출하고 장소와 영상 구간의 관계를
Neo4j에 남기려 한 여행 에이전트 실험. 영상뿐 아니라 블로그, PDF, 웹처럼
서로 다른 포맷의 자료도 같은 그래프에 연동하고자 했다.

1. **청크만으로 사라지는 여행 정보의 관계 남기기**
   - 해결: 국가·지역·영상·영상 구간을 Neo4j 노드와 관계로 연결했다.
   - 배움: 관계 자체가 질문의 핵심이면 그래프가 청킹보다 유용할 수 있다.
   - 한계: 추출 스크립트 수준이며 카탈로그와 서버 정합성 포트는 없었다.

### 버디파이

**개요.** 기존 Nuxt 프론트에서 테크니컬 SEO와 여행 상품 검색, 예약을
진행했다. React Native에서는 Function tool calling으로 여행 계획을 세우는
어시스턴트를 개발했다.

기술적 도전 섹션은 두지 않는다.
